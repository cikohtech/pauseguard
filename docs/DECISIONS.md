# Decisions

Claude Code appends one entry per decision: date, decision, why, and alternatives considered.

- 2026-10-10: Product name "PauseGuard", chosen by Asif. A web search found no existing product with this name (the name "ScamShield" is taken by the Singapore government anti-scam app). The name is kept in a single `PRODUCT_NAME` constant.
- 2026-10-10: LLMs extract and explain; a deterministic fusion policy decides the verdict (explainability, testability, injection resistance).
- 2026-10-10: Gemini 1.5 Flash is retired, so use the current GA Flash model on Vertex AI (verify in phase 00).
- 2026-10-10 (phase 00): **Model = `gemini-3.8-flash`** on the `global` endpoint. It went GA on 2 Sep 2026 and is the newest GA Flash (3.6 and 3.7 Flash are also GA). Why not the kit's default `gemini-2.5-flash`: Google moved its retirement to **16 Oct 2026**, which is before our deadline and inside the evaluation period, so it would break the live demo. Model pages list 3.8 Flash as "Global, Multi-region" (no asia-southeast1), so `GOOGLE_CLOUD_LOCATION=global`, as ARCHITECTURE §3 allows; data stays in asia-southeast1. Breaking changes vs 2.5 that the agent code must respect: `temperature`/`top_p`/`top_k` are **ignored** (determinism comes from `response_schema`); `frequency_penalty`, `presence_penalty` and `candidate_count` **raise errors**; `thinking_budget` is replaced by `thinking_level` (LOW/MEDIUM/HIGH; MINIMAL is rejected); a request whose last turn has the model role fails (no prefill). We default `GEMINI_THINKING_LEVEL=LOW` for latency (p50 ≤ 5 s target) and can raise it per agent if accuracy needs it. Sources: Agent Platform release notes and the Gemini 3.8 Flash developer guide (docs.cloud.google.com), checked 10 Oct 2026. Alternatives: 3.7 Flash (GA 13 Aug), a fallback if 3.8 shows quota or quality issues; it's a one-line env change.
- 2026-10-10 (phase 00): Vertex AI was renamed **Gemini Enterprise Agent Platform** (announced 22 Apr 2026). The old Vertex AI docs are frozen. We still call Gemini through `google-genai` with `GOOGLE_GENAI_USE_VERTEXAI=TRUE`, which is unchanged; we do not use the new `google-cloud-agentplatform` SDK. The deck and README say "Gemini on Vertex AI (Gemini Enterprise Agent Platform)".
- 2026-10-10 (phase 00): **ADK notes (google-adk 2.11.0, google-genai 2.29.0)**:
  1. Imports: `from google.adk.agents import LlmAgent, ParallelAgent, SequentialAgent`; `from google.adk.tools import FunctionTool, AgentTool, google_search`; `from google.adk.runners import Runner, InMemoryRunner`; `from google.adk.sessions import InMemorySessionService`.
  2. `LlmAgent(output_schema=PydanticModel)` **can be combined with tools** in 2.11 (tools run in the thought loop; the schema is enforced only on the final answer). We still validate every result ourselves with the same model (retry once, then the AMBER fallback).
  3. `google_search` is a model built-in tool and **cannot sit next to function tools** in one agent. ADK wraps it automatically only if `GoogleSearchTool(bypass_multi_tools_limit=True)` is used. We follow ARCHITECTURE D4 explicitly: `search_agent = LlmAgent(tools=[google_search])`, and the Scam-Intel agent uses `AgentTool(search_agent, propagate_grounding_metadata=True)` so the source URLs reach `IntelResult.web_findings`.
  4. `Runner(app_name=..., agent=..., session_service=InMemorySessionService())` + `runner.run_async(user_id, session_id, new_message=types.Content(...))`. Parallel evidence + intel: `ParallelAgent` or `asyncio.gather` over two runners, wrapped in `asyncio.wait_for(AGENT_TIMEOUT_SECONDS)`.
  5. Generation settings go in `generate_content_config=types.GenerateContentConfig(thinking_config=types.ThinkingConfig(thinking_level=...))`, never temperature or penalties (see the model entry above).
- 2026-10-10 (phase 00): Schemas use `Literal[...]` enums exactly as in AGENTS_SPEC §0. Additions where the specs left the shape open: `TxnReasonCode` (one code per row of the points table), `TxnFeatures`, `CheckRecord`/`CaseRecord` (Firestore docs), `CaseDetail`, `DecisionResponse.watchlist_added` (drives the "N entities added" toast), `HealthResponse.dependencies`. `CaseFile.recommended_action` uses the analyst actions (RELEASE/HOLD/ESCALATE/REPORT_SCAM), because the case file is written for the analyst. An invalid `box_2d` is set to `None` by the validator rather than failing the whole `EvidenceAnalysis`. Word limits for the Explainer are enforced in post-processing, not in the schema, so long text is trimmed instead of triggering the fallback.

Unimplemented Make targets (seed, eval, deploy, smoke) exit 1 with the phase that fills them in, so nobody mistakes them for success. `pre-commit` is a backend dev dependency, so the git hook points at a stable interpreter.
- 2026-10-10 (phase 00): Before the first commit, moved `reference/idea-research.md`, `reference/concept-deep-dive.md` and the "Likely judge questions" section of SUBMISSION_DECK.md into the git-ignored `private/`, so they never enter git history. Phase 11 task 9 is therefore already done, and no `git filter-repo` will be needed.
- 2026-10-10 (phase 01): **Generator** (`data/generate/make_synthetic.py`) is stdlib-only. Every customer gets its own RNG (`"<seed>:<customer_id>"`), so the personas don't change when `--customers` does. Output is byte-identical for the same `--seed`/`--customers`/`--end-date`. `--end-date` **defaults to today (SGT)**, and history stops at 00:00 SGT that day, so every `make seed-*` gives the live demo a full 90-day window. The tests pin the date (2026-10-10). The CSVs are git-ignored and rebuilt in about 1 s. Alternatives: a fixed anchor date (the 90-day window would drain during judging) or shifting timestamps at load time (more moving parts).
- 2026-10-10 (phase 01): "About 3% scam episodes" is read as **3% of generated customers** (15 of 497), one episode each, with typologies cycling GOV ×4, INVESTMENT ×3, JOB_TASK ×3, ECOMMERCE ×2, FAKE_FRIEND, ROMANCE, BEC_INVOICE. Eligibility: GOV for ages 50+, job scams for 40 and under, BEC for SME owners. Hard negatives are deliberate, so no single feature decides: one-off payments to brand-new legit payees (15% of customers), legit crypto buyers, big card purchases, payees that were added but never paid, and about 2% late-night activity. `cust_004` is reserved for the analyst, so the generated customers are `cust_005`–`cust_501`.
- 2026-10-10 (phase 01): The watchlist seed has Mrs Tan's scammer phone (`+65 8000 0147`) and mule account (`123-45678-9`), so WATCHLIST_MATCH fires. Her scam domain `mas-gov-verify.example` is **deliberately left out**, so the Scam-Intel agent has an unknown domain to check with Google Search grounding in the demo.
- 2026-10-10 (phase 01): **TransactionRepo** is synchronous (sqlite3 and the BigQuery client are sync; async callers use `asyncio.to_thread`). On top of the five methods in the prompt it has `risk_snapshot()`, which returns every input of `compute_txn_risk` in **one query** (one BigQuery round trip toward the 300 ms target), plus `ping()` for `/healthz`. Every method takes `as_of` so the benchmark is reproducible. The returned models have no `is_scam_label`/`scam_typology_label` fields, so the risk tool can't read ground truth. Window rules are written down once in `data/base.py` and checked against a brute-force Python reference. Account numbers are compared normalised (`REPLACE`/`UPPER` in both SQL dialects).
- 2026-10-10 (phase 01): **StateRepo** is async (Firestore `AsyncClient`). An in-memory twin (`STATE_BACKEND=memory`) stores the same serialised documents, and one contract suite runs against both: always on memory, and on the emulator when it's reachable, using the separate `demo-pauseguard-test` project, which is wiped per test. Locally the Firestore project is always `demo-pauseguard` (matching the emulator), whatever `.env` says. `update_*` raises `NotFoundError` for a missing document.
- 2026-10-10 (phase 01): **Watchlist IDs** are the normalised value, with `/` percent-encoded (Firestore IDs can't contain `/`); a URL with no path shares its domain's document. `upsert_watchlist` is atomic without a transaction: `create()`, then on AlreadyExists `Increment(1)` + `ArrayUnion`. An existing entry **keeps its source**, so the 6-hourly reset (delete `source=ANALYST_REPORT`) never removes a seed entry, even after an analyst re-reports it.
- 2026-10-10 (phase 01): Added a `personas/{customer_id}` collection (DEPLOYMENT §1 says seed-cloud loads "personas"; DATA_SPEC §3 didn't list it). Added `infra/firestore.indexes.json` for the three filtered and ordered queries and referenced it from `firebase.json`. The DEPLOYMENT deploy line now includes `firestore:indexes`. In BigQuery, `transactions` is partitioned by day on `ts` and clustered by `customer_id`. `checks_analytics` is created once and never truncated by a re-seed.
- 2026-10-10 (phase 01): **Local tooling.** `npm i -g firebase-tools` failed (root-owned global prefix), so the Makefile uses a global `firebase` if one exists and otherwise `npx --yes firebase-tools@15.31.0` (released 23 Sep 2026), with no sudo needed. `brew install openjdk@21` is keg-only, so the Makefile puts `/opt/homebrew/opt/openjdk@21/bin` on PATH when it exists. The BigQuery parity test (`-m live`) loads the test CSVs into a throwaway dataset, compares every query with SQLite, and drops the dataset. It can only run once a GCP project exists (row 7).
