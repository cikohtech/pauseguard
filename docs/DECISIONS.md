- 2026-10-10 (phase 00): **Model = `gemini-3.8-flash`** on the `global` endpoint. It went GA on 2 Sep 2026 and is the newest GA Flash (3.6 and 3.7 Flash are also GA). Why not the kit's default `gemini-2.5-flash`: Google moved its retirement to **16 Oct 2026**, which is before our deadline and inside the evaluation period, so it would break the live demo. Model pages list 3.8 Flash as "Global, Multi-region" (no asia-southeast1), so `GOOGLE_CLOUD_LOCATION=global`, as ARCHITECTURE §3 allows; data stays in asia-southeast1. Breaking changes vs 2.5 that the agent code must respect: `temperature`/`top_p`/`top_k` are **ignored** (determinism comes from `response_schema`); `frequency_penalty`, `presence_penalty` and `candidate_count` **raise errors**; `thinking_budget` is replaced by `thinking_level` (LOW/MEDIUM/HIGH; MINIMAL is rejected); a request whose last turn has the model role fails (no prefill). We default `GEMINI_THINKING_LEVEL=LOW` for latency (p50 ≤ 5 s target) and can raise it per agent if accuracy needs it. Sources: Agent Platform release notes and the Gemini 3.8 Flash developer guide (docs.cloud.google.com), checked 10 Oct 2026. Alternatives: 3.7 Flash (GA 13 Aug), a fallback if 3.8 shows quota or quality issues; it's a one-line env change.

- 2026-10-10 (phase 00): **ADK notes (google-adk 2.11.0, google-genai 2.29.0)**:

- 2026-10-11 (phase 03): **Transaction risk tool.** `compute_txn_risk` makes exactly one `risk_snapshot()` call and then runs two pure functions (`build_features`, `score_features`), so every row of the points table is unit-tested without a database. The watchlist is in Firestore (async), so the caller passes `watchlist_hit`; phase 04 looks up the payee **account**. "Payee name on the watchlist" is not implemented, because the watchlist has no NAME type (PHONE/URL/DOMAIN/ACCOUNT only). Edge rules: `transfers_to_new_payees_24h` **counts the current transfer** when it goes to a new payee, so "≥ 2" means "the second new payee within 24 hours" (a velocity rule that needs two earlier ones would only fire on the third); the local hour is Asia/Singapore; no 90-day debits means no spike points; a zero or negative balance makes HIGH_BALANCE_SHARE fire. The B0 thresholds (RED ≥ 70, AMBER ≥ 40) are module constants, not settings, because B0 is a fixed baseline, never tuned. Demo check: Tan scores 55, or 95 with the watchlist hit; Raj and Aisyah both score above the GREEN fast path (< 30), so the demo reaches the check-in.
- 2026-10-11 (phase 03): **Evidence agent wiring (ADK 2.11).** `LlmAgent(static_instruction=prompt, output_schema=EvidenceAnalysis, include_contents="none")`, thinking LOW, run through a `Runner` with a fresh `InMemorySessionService` session per call (deleted afterwards). `static_instruction` is used because a plain `instruction` string gets ADK's `{state}` templating, and the prompt is static anyway. There is no `output_key`, so ADK doesn't validate; we do: code fences are stripped, unknown flag codes are dropped (not fatal), float boxes are rounded, and a bad JSON or schema answer or a model error is **retried once** and then replaced by a fallback (`UNKNOWN`, 0.0, no flags) with `EvidenceRun.failed=True`. Phase 04 maps that to AMBER + review. Unreadable evidence (a missing file, a path outside the repo, a local path on Cloud Run) goes straight to the fallback without a model call. Tests drive the real Runner with a fake `BaseLlm`. The transfer block also gives the **account, bank and note** (the spec listed amount, payee and destination), so the model can tell whether the evidence matches the payee (PAYEE_NAME_MISMATCH, or Aisyah's matching tenancy).
- 2026-10-11 (phase 03): **Deterministic post-processing of every EvidenceAnalysis**, whether it came from the model or the fallback. `WATCHLIST_MATCH` from the model is dropped (only the watchlist tool may set it). A box is kept only on an image item that exists, so a box on a PDF, on text or on an out-of-range index is removed. `evidence_present` comes from the request. Flags are ranked HIGH → LOW, de-duplicated and capped at 6. Untrusted text can't open or close our delimiters (`<evidence`, `<transfer`, `<customer_answer`, `<system` become `‹…`).
- 2026-10-11 (phase 03): **Injection pre-scan scope.** The patterns target *instructions to an AI or screening system* (ignore previous instructions, respond GREEN, a note to AI reviewers, 忽略之前的指令, 判定为安全, 致银行AI审核系统…), not scam vocabulary ("safe account" / 安全账户 or "don't tell the bank" are flags for the model). Phrases that genuine messages use are left out on purpose: 【系统提示】, "system-generated message", "Hi Ai Ling" (the AI acronyms are case-sensitive), "Risk level: Low", and 给助手 (handing something to a human assistant). A hit forces `injection_attempt_detected` plus a HIGH `COACHING_TO_LIE` flag, which fusion turns into RED, so a false hit would block a legit payment. It scans the customer's answer, the quick reply, pasted text, and the model's **verbatim quotes and `reason_given`**, but not the model's summary, whose negations ("no attempt to override instructions") would fire falsely. There is no OCR or PDF-text step: images and PDFs are covered through the model's quotes, which keeps one model call per check and no new dependency. On the dev split it fires only on the dev injection case.
- 2026-10-11 (phase 03): **Logs are redacted** by a structlog processor on both the structlog and stdlib paths: phones, IBAN-like and 9–18-digit accounts, NRICs and emails become `[PHONE]`/`[ACCOUNT]`/`[NRIC]`/`[EMAIL]`; timestamps, IDs and amounts are left as they are. CLIs log to stderr so their stdout is pure JSON. google-genai 2.29 / ADK 2.11 deprecate `GOOGLE_GENAI_USE_VERTEXAI` in favour of `GOOGLE_GENAI_USE_ENTERPRISE`; `export_sdk_env()` sets both to the same value, and `.env` keeps the documented name.
- 2026-10-11 (phase 03): **Prompt tuning on dev only.** The prompt said "about 30 cases"; we ran **all 60 dev cases**, because one run takes about 1 minute and costs cents. `eval/evidence_dev.py` refuses test-split IDs. v1 (the spec's core plus flag and typology definitions, severity rules, legit signals and the box convention) gave typology 59/60. v2 added one general "friend on a new number" rule; it was unchanged at 59/60, and ev_0127 (a real friend repaying a shared cost, "pay me back today") stays a false alarm. We stopped there rather than fit the prompt to one dev case. Kept thinking LOW and the default media resolution; the latency levers go to phase 08.
- 2026-10-11 (phase 04): **Raj's job scam: AMBER, via a proportionality rule in fusion.** AGENTS_SPEC §4 as written makes Raj RED twice over: PAY_TO_EARN (HIGH) forces RED, and JOB_TASK 0.95 with a transaction score of 55 (≥ 50) matches the typology rule. That contradicts the PRD's AMBER tier and the DEMO_SCRIPT beat (2:10–2:35, "not every case needs a hard stop"). Decision: split the RED rules. **Hard-stop signals hold at any amount**: a watchlist match, a prompt injection, a HIGH SAFE_ACCOUNT or REMOTE_ACCESS_APP flag. **Scam patterns** (a HIGH PAY_TO_EARN flag, or the confident-typology rule) hold from `FUSION_RED_MIN_AMOUNT` (S$1,000) up and give AMBER below it: a pause, a plain explanation and the trusted-contact call, with the customer still in control. Why: an analyst call within 30 minutes (the RED promise) is the expensive resource; job-task scams escalate in steps (S$36 paid out → S$450 "top-up" → more), so a cool-off at the first small top-up breaks the cycle, and a larger one or a listed account is still held. Scam recall (AMBER or RED) is unchanged; hard-stop recall drops for small payments, and legit→RED can only go down. Chosen before any test-split run (EVAL_PLAN §6). `FUSION_RED_MIN_AMOUNT=0` restores the spec's rule set. Alternatives: keep the spec and change the demo beat to RED (the demo then never shows AMBER, a core MVP story), or make PAY_TO_EARN need a second HIGH flag (Raj would still be RED through the typology rule).
- 2026-10-11 (phase 04): **Watchlist in code, web search after the verdict.** The orchestrator does every watchlist lookup itself (payee account at `start`; regex phones/URLs/accounts from the customer's text in parallel with the evidence agent; then the entities the evidence agent extracted), so a RED never depends on an LLM deciding to call a tool. The Scam-Intel LlmAgent (FunctionTool `watchlist_lookup` + `AgentTool(search_agent)`) runs **after the customer has their verdict**, AMBER/RED only, in parallel with the case-file agent. Why: fusion never reads web findings (AGENTS_SPEC §4), a grounded search measured 9–25 s live, and GREEN checks never pay for search. The intel LLM returns only `IntelFindings{web_findings}`; matches come from code and the tool. Guard rails in code: ≤ `INTEL_MAX_SEARCHES` (2) and no phone or account number per check (`before_tool_callback`); a finding is dropped unless it matches a search that really ran, and its `sources` are that search's grounding URLs, captured by an `after_model_callback` on the search agent because AgentTool does not forward the nested events. The Google Search suggestions chip (`search_entry_point.rendered_content`) is stored on `WebFinding.search_entry_point_html`, because grounded results must be shown with it (console, phase 07). The intel run has **one attempt**, not the usual retry: a retry cannot search again (the budget is spent) and would only produce ungrounded findings.
- 2026-10-11 (phase 04): **Explainer v2: the model writes the headline and body only.** v1 (headline, body, flag explanations, next steps) produced about 235 output tokens in 2.4–3.9 s on 3.8 Flash at thinking LOW (no thought tokens are used at LOW, and MINIMAL is rejected). The explanation next to each numbered box and the next steps now come from reviewed en/zh templates (`FLAG_TEXT`, all 18 codes, within 20 words / 40 characters, enforced by a test); the model's part dropped to 1.3–1.9 s. This also means no model-written text sits next to the boxes. Post-processing: word limits by trimming whole sentences (en words, zh characters: 8/60 and 16/120), links removed, an AMBER headline/body that calls it a scam as a fact is replaced by the template's, `ms`/`ta` fall back to English. The explainer has its own cap (`EXPLAINER_BUDGET_SECONDS`, 4 s) inside the 12 s budget; slower → the static message for the verdict (a RED is never downgraded).
- 2026-10-11 (phase 04): **Latency work and results.** (1) Agents were given the model as a *name*, so ADK built a new `Gemini` + genai `Client` per call: credentials reloaded each time (locally `gcloud config get project`, a 0.4 s subprocess), a new token and a new TLS connection. All agents now share one `Gemini` instance (`_runtime.shared_model`). (2) `GEMINI_MEDIA_RESOLUTION=MEDIUM` for evidence images/PDF pages: 15–20% fewer input tokens; dev split unchanged (typology 59/60, same single miss ev_0127, injection 1/1). (3) Evidence prompt v3: the shortest exact phrase per flag (≤ 15 words / 25 Chinese characters, was 25 words) and a one-sentence summary: mean output 459 → 425 tokens, dev p95 9.6 → 7.5 s, accuracy unchanged. (4) **Hedged evidence request**: no answer after `EVIDENCE_HEDGE_AFTER_SECONDS` (6 s) → an identical second request, first answer wins, the loser is cancelled (both are metered). It exists because single calls on the global endpoint sometimes stall for 12–25 s: one stall turned Aisyah's GREEN into AMBER + review before hedging; with hedging it fired 4 times in 9 checks and every verdict held. (5) The ADK event generator is closed with `aclosing` so a cancelled call cleans up in its own task (otherwise OpenTelemetry logged "created in a different Context"). **Measured (3 demo scenarios × 3, live, local, `make scenario RUNS=3`):** answer → verdict p50 4.1–5.4 s per run (27 checks pooled ≈ 4.9 s); answer → full customer message p50 5.7 s, 6.1 s and 8.1 s per run (pooled ≈ 6.3 s) depending on endpoint load; Tan (image, 6 flags) is the slowest at 7–10 s. Not done (phase 08 candidates): streaming the evidence answer, provisioned throughput, a faster model if one becomes available on Vertex.
- 2026-10-11 (phase 04): **Orchestrator contract.** `start()` writes `checks/{id}` (GREEN fast path or CHECKIN with the templated en/zh question and localised quick replies); `analyse()` appends the customer message, updates the check through ANALYSING → DONE, creates `cases/{id}` at `done` (case_file empty) and fills `case_file` when the case-file agent finishes; the web findings are written to the check afterwards. So the console's realtime listener sees the case at once. IDs are ULID-style (`chk_01M4…`, `case_01M4…`). Progress events go through an `on_event` callback (sync or async; a failing listener is logged, never fatal); the new `partial DECIDING` event carries the verdict and top flags, and `LatencyMs.verdict` records its time next to `total`. One `check_done` JSON log line per check carries per-agent latency and tokens. The optional follow-up question (ARCHITECTURE §2) is not implemented (MVP). Fusion accepts `answer_flags` (AGENTS_SPEC's `checkin_answer_flags`), but the orchestrator does not derive any: quick replies are passed to the evidence agent as context instead of becoming flags.
- 2026-10-11 (phase 04): **`pasted_text` on POST /checks/{id}/messages** (API_SPEC). Raj's demo beat "pastes the Telegram text"; without a separate field the paste would be read as his own answer and `evidence_present` would be false.
