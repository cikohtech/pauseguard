Claude Code appends one entry per decision: date, decision, why, and alternatives considered.

- 2026-10-10: Gemini 1.5 Flash is retired, so use the current GA Flash model on Vertex AI (verify in phase 00).
- 2026-10-10 (phase 00): **Model = `gemini-3.8-flash`** on the `global` endpoint. It went GA on 2 Sep 2026 and is the newest GA Flash (3.6 and 3.7 Flash are also GA). Why not the kit's default `gemini-2.5-flash`: Google moved its retirement to **16 Oct 2026**, which is before our deadline and inside the evaluation period, so it would break the live demo. Model pages list 3.8 Flash as "Global, Multi-region" (no asia-southeast1), so `GOOGLE_CLOUD_LOCATION=global`, as ARCHITECTURE §3 allows; data stays in asia-southeast1. Breaking changes vs 2.5 that the agent code must respect: `temperature`/`top_p`/`top_k` are **ignored** (determinism comes from `response_schema`); `frequency_penalty`, `presence_penalty` and `candidate_count` **raise errors**; `thinking_budget` is replaced by `thinking_level` (LOW/MEDIUM/HIGH; MINIMAL is rejected); a request whose last turn has the model role fails (no prefill). We default `GEMINI_THINKING_LEVEL=LOW` for latency (p50 ≤ 5 s target) and can raise it per agent if accuracy needs it. Sources: Agent Platform release notes and the Gemini 3.8 Flash developer guide (docs.cloud.google.com), checked 10 Oct 2026. Alternatives: 3.7 Flash (GA 13 Aug), a fallback if 3.8 shows quota or quality issues; it's a one-line env change.
- 2026-10-10 (phase 00): Vertex AI was renamed **Gemini Enterprise Agent Platform** (announced 22 Apr 2026). The old Vertex AI docs are frozen. We still call Gemini through `google-genai` with `GOOGLE_GENAI_USE_VERTEXAI=TRUE`, which is unchanged; we do not use the new `google-cloud-agentplatform` SDK. The deck and README say "Gemini on Vertex AI (Gemini Enterprise Agent Platform)".
- 2026-10-10 (phase 00): **ADK notes (google-adk 2.11.0, google-genai 2.29.0)**:
  1. Imports: `from google.adk.agents import LlmAgent, ParallelAgent, SequentialAgent`; `from google.adk.tools import FunctionTool, AgentTool, google_search`; `from google.adk.runners import Runner, InMemoryRunner`; `from google.adk.sessions import InMemorySessionService`.
  2. `LlmAgent(output_schema=PydanticModel)` **can be combined with tools** in 2.11 (tools run in the thought loop; the schema is enforced only on the final answer). We still validate every result ourselves with the same model (retry once, then the AMBER fallback).
  3. `google_search` is a model built-in tool and **cannot sit next to function tools** in one agent. ADK wraps it automatically only if `GoogleSearchTool(bypass_multi_tools_limit=True)` is used. We follow ARCHITECTURE D4 explicitly: `search_agent = LlmAgent(tools=[google_search])`, and the Scam-Intel agent uses `AgentTool(search_agent, propagate_grounding_metadata=True)` so the source URLs reach `IntelResult.web_findings`.
  4. `Runner(app_name=..., agent=..., session_service=InMemorySessionService())` + `runner.run_async(user_id, session_id, new_message=types.Content(...))`. Parallel evidence + intel: `ParallelAgent` or `asyncio.gather` over two runners, wrapped in `asyncio.wait_for(AGENT_TIMEOUT_SECONDS)`.
  5. Generation settings go in `generate_content_config=types.GenerateContentConfig(thinking_config=types.ThinkingConfig(thinking_level=...))`, never temperature or penalties (see the model entry above).

- 2026-10-10 (phase 01): **Generator** (`data/generate/make_synthetic.py`) is stdlib-only. Every customer gets its own RNG (`"<seed>:<customer_id>"`), so the personas don't change when `--customers` does. Output is byte-identical for the same `--seed`/`--customers`/`--end-date`. `--end-date` **defaults to today (SGT)**, and history stops at 00:00 SGT that day, so every `make seed-*` gives the live demo a full 90-day window. The tests pin the date (2026-10-10). The CSVs are git-ignored and rebuilt in about 1 s. Alternatives: a fixed anchor date (the 90-day window would drain during judging) or shifting timestamps at load time (more moving parts).
- 2026-10-10 (phase 01): "About 3% scam episodes" is read as **3% of generated customers** (15 of 497), one episode each, with typologies cycling GOV ×4, INVESTMENT ×3, JOB_TASK ×3, ECOMMERCE ×2, FAKE_FRIEND, ROMANCE, BEC_INVOICE. Eligibility: GOV for ages 50+, job scams for 40 and under, BEC for SME owners. Hard negatives are deliberate, so no single feature decides: one-off payments to brand-new legit payees (15% of customers), legit crypto buyers, big card purchases, payees that were added but never paid, and about 2% late-night activity. `cust_004` is reserved for the analyst, so the generated customers are `cust_005`–`cust_501`.

- 2026-10-10 (phase 01): **TransactionRepo** is synchronous (sqlite3 and the BigQuery client are sync; async callers use `asyncio.to_thread`). On top of the five methods in the prompt it has `risk_snapshot()`, which returns every input of `compute_txn_risk` in **one query** (one BigQuery round trip toward the 300 ms target), plus `ping()` for `/healthz`. Every method takes `as_of` so the benchmark is reproducible. The returned models have no `is_scam_label`/`scam_typology_label` fields, so the risk tool can't read ground truth. Window rules are written down once in `data/base.py` and checked against a brute-force Python reference. Account numbers are compared normalised (`REPLACE`/`UPPER` in both SQL dialects).
- 2026-10-10 (phase 01): **StateRepo** is async (Firestore `AsyncClient`). An in-memory twin (`STATE_BACKEND=memory`) stores the same serialised documents, and one contract suite runs against both: always on memory, and on the emulator when it's reachable, using the separate `demo-pauseguard-test` project, which is wiped per test. Locally the Firestore project is always `demo-pauseguard` (matching the emulator), whatever `.env` says. `update_*` raises `NotFoundError` for a missing document.
- 2026-10-10 (phase 01): **Watchlist IDs** are the normalised value, with `/` percent-encoded (Firestore IDs can't contain `/`); a URL with no path shares its domain's document. `upsert_watchlist` is atomic without a transaction: `create()`, then on AlreadyExists `Increment(1)` + `ArrayUnion`. An existing entry **keeps its source**, so the 6-hourly reset (delete `source=ANALYST_REPORT`) never removes a seed entry, even after an analyst re-reports it.

- 2026-10-10 (phase 02): **Who drafted the eval messages.** `make_eval_messages.py --drafter gemini` sends the seed prompts (`data/generate/prompts/`) plus each slot to `GEMINI_MODEL` with the `Draft` schema. It could not run yet: the GCP project only arrives at row 7. Waiting for it would push the eval set behind the agents, and the point of phase 02 is to freeze the set before the agents exist. - 2026-10-10 (phase 02): **The eval plan comes from code** (seed 42), so the DATA_SPEC §4 mix is exact. Case IDs are shuffled, so they don't reveal the label. Each case uses a different real customer of the synthetic bank (`cust_005`–`cust_501`), never a demo persona and never one of the 15 scam-episode customers, so `compute_txn_risk` works on them. 30 legit cases pay an **existing** payee (`is_new_payee=false`, taken from `payees.csv`); this was checked to hold after a re-seed with a different `--end-date`, because customers and payees don't depend on the date. `expected_verdict_min` is GREEN for LEGIT, AMBER for SCAM and RED for the 5 injection cases (SECURITY_PRIVACY §1: injection forces RED). `quick_reply` may be null when no chip fits (for example "the bank's fraud officer").

- 2026-10-10 (phase 02): **Renderer and freeze.** `render_chats.py` uses Python Playwright, which lives in a `datagen` dependency group (`make playwright`), so it stays out of the API image. Screens are 360×640 CSS px at device scale 3 (1080×1920) with generic, unbranded chat, SMS and email styling. A long thread shrinks its font (down to 10 px) instead of being cropped, so no evidence is cut off. Documents are A4 PDFs printed by Chromium, with extractable text. `eval/TEST_SPLIT_HASH` is a SHA-256 over the canonical JSON of the 100 test cases **plus the SHA-256 of every evidence file they reference**, so changing a screenshot also breaks the freeze. It is checked by `make eval-verify` and pytest. Fonts are system fonts (PingFang SC on macOS), so re-rendering on another OS changes the bytes. The PNGs are committed and never need re-rendering.

- 2026-10-10 (phase 02): **Frozen.** The user approved `data/eval/REVIEW.md` as is. `make eval-dataset` rendered 96 PNGs and 16 PDFs and wrote `cases.jsonl` (160) and `eval/TEST_SPLIT_HASH` (`f1c1155d…`). Chromium stamps a creation date into PDFs, so re-rendering can never reproduce the bytes. `render_chats.py` and `assemble` therefore **refuse to overwrite a frozen set** without `--force`; a changed test split must be reported as a new split (EVAL_PLAN §6).
- 2026-10-11 (phase 03): **Transaction risk tool.** `compute_txn_risk` makes exactly one `risk_snapshot()` call and then runs two pure functions (`build_features`, `score_features`), so every row of the points table is unit-tested without a database. The watchlist is in Firestore (async), so the caller passes `watchlist_hit`; phase 04 looks up the payee **account**. "Payee name on the watchlist" is not implemented, because the watchlist has no NAME type (PHONE/URL/DOMAIN/ACCOUNT only). Edge rules: `transfers_to_new_payees_24h` **counts the current transfer** when it goes to a new payee, so "≥ 2" means "the second new payee within 24 hours" (a velocity rule that needs two earlier ones would only fire on the third); the local hour is Asia/Singapore; no 90-day debits means no spike points; a zero or negative balance makes HIGH_BALANCE_SHARE fire. The B0 thresholds (RED ≥ 70, AMBER ≥ 40) are module constants, not settings, because B0 is a fixed baseline, never tuned. Demo check: Tan scores 55, or 95 with the watchlist hit; Raj and Aisyah both score above the GREEN fast path (< 30), so the demo reaches the check-in.
- 2026-10-11 (phase 03): **Evidence agent wiring (ADK 2.11).** `LlmAgent(static_instruction=prompt, output_schema=EvidenceAnalysis, include_contents="none")`, thinking LOW, run through a `Runner` with a fresh `InMemorySessionService` session per call (deleted afterwards). `static_instruction` is used because a plain `instruction` string gets ADK's `{state}` templating, and the prompt is static anyway. There is no `output_key`, so ADK doesn't validate; we do: code fences are stripped, unknown flag codes are dropped (not fatal), float boxes are rounded, and a bad JSON or schema answer or a model error is **retried once** and then replaced by a fallback (`UNKNOWN`, 0.0, no flags) with `EvidenceRun.failed=True`. Phase 04 maps that to AMBER + review. Unreadable evidence (a missing file, a path outside the repo, a local path on Cloud Run) goes straight to the fallback without a model call. Tests drive the real Runner with a fake `BaseLlm`. The transfer block also gives the **account, bank and note** (the spec listed amount, payee and destination), so the model can tell whether the evidence matches the payee (PAYEE_NAME_MISMATCH, or Aisyah's matching tenancy).
- 2026-10-11 (phase 03): **Deterministic post-processing of every EvidenceAnalysis**, whether it came from the model or the fallback. `WATCHLIST_MATCH` from the model is dropped (only the watchlist tool may set it). A box is kept only on an image item that exists, so a box on a PDF, on text or on an out-of-range index is removed. `evidence_present` comes from the request. Flags are ranked HIGH → LOW, de-duplicated and capped at 6. Untrusted text can't open or close our delimiters (`<evidence`, `<transfer`, `<customer_answer`, `<system` become `‹…`).
- 2026-10-11 (phase 03): **Injection pre-scan scope.** The patterns target *instructions to an AI or screening system* (ignore previous instructions, respond GREEN, a note to AI reviewers, 忽略之前的指令, 判定为安全, 致银行AI审核系统…), not scam vocabulary ("safe account" / 安全账户 or "don't tell the bank" are flags for the model). Phrases that genuine messages use are left out on purpose: 【系统提示】, "system-generated message", "Hi Ai Ling" (the AI acronyms are case-sensitive), "Risk level: Low", and 给助手 (handing something to a human assistant). A hit forces `injection_attempt_detected` plus a HIGH `COACHING_TO_LIE` flag, which fusion turns into RED, so a false hit would block a legit payment. It scans the customer's answer, the quick reply, pasted text, and the model's **verbatim quotes and `reason_given`**, but not the model's summary, whose negations ("no attempt to override instructions") would fire falsely. There is no OCR or PDF-text step: images and PDFs are covered through the model's quotes, which keeps one model call per check and no new dependency. On the dev split it fires only on the dev injection case.
- 2026-10-11 (phase 03): **Logs are redacted** by a structlog processor on both the structlog and stdlib paths: phones, IBAN-like and 9–18-digit accounts, NRICs and emails become `[PHONE]`/`[ACCOUNT]`/`[NRIC]`/`[EMAIL]`; timestamps, IDs and amounts are left as they are. CLIs log to stderr so their stdout is pure JSON. google-genai 2.29 / ADK 2.11 deprecate `GOOGLE_GENAI_USE_VERTEXAI` in favour of `GOOGLE_GENAI_USE_ENTERPRISE`; `export_sdk_env()` sets both to the same value, and `.env` keeps the documented name.
- 2026-10-11 (phase 03): **Prompt tuning on dev only.** The prompt said "about 30 cases"; we ran **all 60 dev cases**, because one run takes about 1 minute and costs cents. `eval/evidence_dev.py` refuses test-split IDs. v1 (the spec's core plus flag and typology definitions, severity rules, legit signals and the box convention) gave typology 59/60. v2 added one general "friend on a new number" rule; it was unchanged at 59/60, and ev_0127 (a real friend repaying a shared cost, "pay me back today") stays a false alarm. We stopped there rather than fit the prompt to one dev case. Kept thinking LOW and the default media resolution; the latency levers go to phase 08.
