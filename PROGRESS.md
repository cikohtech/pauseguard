Row 7 still runs `infra/setup.sh` (the other APIs, Firestore DB, BigQuery dataset, bucket, service account, secrets).
- The Firestore emulator keeps data in memory. After (re)starting `make dev` or `make emulators`, run `make seed-local` again (about 2 s) so the watchlist and personas are back.
- **Not yet run:** the BigQuery parity test (`uv --directory backend run pytest -m live -k bigquery`) and `make seed-cloud`. Both need the GCP project from row 7. `make seed-cloud` regenerates the data with today's date, so run it again on 17 Oct (row 12) so the 90-day window is fresh for judging.
- `npm audit` reports 7 "high" issues, all in the `shadcn` CLI's build-time tree (micromatch via fast-glob/ts-morph). None of it ships to the browser. Don't run `npm audit fix --force` (it downgrades shadcn); re-check when shadcn publishes a fix.
- Starlette warns that `httpx` in `TestClient` is deprecated in favour of `httpx2`. It's harmless for now.
- ~~Spec conflict for phase 04 (Raj AMBER vs RED).~~ Resolved in phase 04: hard-stop signals are RED at any amount; scam patterns (PAY_TO_EARN, a confident typology) are RED from S$1,000 and AMBER below (`FUSION_RED_MIN_AMOUNT`, DECISIONS 2026-10-11). AGENTS_SPEC §4 updated.
- Eval renders use macOS system fonts (PingFang SC). Re-rendering on another OS changes the PNG bytes and breaks `eval/TEST_SPLIT_HASH`; the rendered files are committed, so don't re-render them.
- `/healthz` doesn't check its dependencies yet (Firestore, BigQuery, model); that's planned for phase 10 (DEPLOYMENT §7).
- ~~For phase 04 (from phase 03)~~: done. A failed or timed-out evidence run → AMBER + `needs_review`; the payee account is looked up at `start` (in parallel with the risk query, via `risk_from_snapshot`); Raj decided (above).
- **Latency (phase 04, live, local):** answer → verdict p50 4.1–5.4 s per 9-check run; answer → full customer message p50 5.7 s / 6.1 s / 8.1 s across three runs (pooled ≈ 6.3 s vs the ≤ 6 s target). The evidence call dominates and its speed varies with load on the `global` endpoint (Tan's image: 5–10 s). Single calls sometimes stall for 12–25 s; the evidence call is hedged at 6 s, and the 12 s budget's safe fallback (AMBER + review) covers the rest. Already applied: shared Gemini client, media MEDIUM, evidence prompt v3, explainer v2 (headline/body only) with a 4 s cap. Left for phase 08: streaming the evidence answer, provisioned throughput, re-measuring from Cloud Run (asia-southeast1) once deployed.
- ~~**For phase 05 (API):**~~ done (see DECISIONS 2026-10-11 phase 05). Call `Orchestrator.start()` from POST /checks and `Orchestrator.analyse(check_id, msg, on_event=...)` from POST /checks/{id}/messages; map `CheckStateError` → 409 and `NotFoundError` → 404. The orchestrator already persists the check (status, evidence, intel, fusion, message, latency, tokens) and the case, so the API's `on_event` only needs to feed SSE (or the MVP's polling, which reads the check doc). `analyse()` returns after the case file (up to `CASEFILE_TIMEOUT_SECONDS` = 25 s after `done`): either respond from the `done` event and keep the task running (Cloud Run then needs CPU always allocated), or keep the request open until the case file is written (simplest; the UI polls and sees DONE at `done`). New request field: `pasted_text`.
- **For phase 07 (console):** web findings carry `search_entry_point_html`, the Google Search suggestions chip; grounded results must be displayed with it (render it in a sandboxed iframe next to the Intel tab's findings). The case document exists from `done` with `case_file: null`; the summary fills in a few seconds later.
- The Scam-Intel agent's grounded search takes 9–25 s live and sometimes hits the 25 s budget; then the case has watchlist intel but no web findings (logged as `intel_failed`). It never affects the verdict.
- The orchestrator CLI (`make scenario`) writes its checks and cases into the Firestore emulator when it is running (else into memory), and seeds the watchlist and personas itself if they are missing.
- **Gemini 3.8 Flash latency, 11 Oct afternoon (phase 05 acceptance):** raw evidence calls on file evidence took **18–28 s** on the `global` endpoint (phase 04 measured 4–10 s); the same Aisyah PDF on `gemini-3.7-flash` took 4.3 s with the same answer. With the 12 s budget, `make demo-curl` gave Tan RED (via the watchlist hard stop, evidence timed out on the 2nd run), Raj AMBER (7 s, text only), and **Aisyah AMBER + needs_review** (the designed safe fallback, never GREEN). With `AGENT_TIMEOUT_SECONDS=45` the same script and `make api-live` gave the expected RED / AMBER / GREEN (Tan 27 s, Raj 11 s, Aisyah 18 s) and "3 entities added". The API layer adds no measurable time (the CLI without the API timed out the same way). **Decision needed before the demo (phase 08 at the latest):** stay on 3.8 Flash and re-measure from Cloud Run, or switch `GEMINI_MODEL` to `gemini-3.7-flash` (re-run `make evidence-dev` first; the test split is frozen, the model is not).
- The local Firestore emulator holds 30+ open cases from `make scenario` and `make demo-curl` runs. `POST /api/v1/admin/reset-demo` (with `X-Admin-Token`) clears the personas' checks and cases, or restart the emulator and run `make seed-local`.
